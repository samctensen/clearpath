# AI second opinion: implementation and evaluation

Verified November 3, 2026, Pacific time. Sam requested an OpenAI opinion on marketing offers and selected compliance and marketing feedback, shown separately. This is optional assistance within the existing review workflow, not a hiring requirement or an automated legal decision.

## Shipped behavior

The submission page generates both opinions on demand for the current saved revision. Results persist separately in Postgres with revision, copy hash, model, prompt version, and generation time. Reopening a result reuses it; historical results remain available. Only an explicit reviewer action promotes a concern into the existing manual-concern workflow. Neither generation nor suggested wording changes copy, deterministic analysis, case status, approval, or the activity history. A human promotion is recorded normally.

The Deno API uses the [OpenAI Responses API with structured output](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), defaulting to [gpt-5.4-mini-2026-03-17](https://developers.openai.com/api/docs/models/gpt-5.4-mini). Release prompt: `clearpath-second-opinion-v5`; reasoning: medium; output cap: 4,000 tokens; timeout: 40 seconds; `store: false`; no tools or automatic retries. The API validates the schema, exact quotations from submitted copy, and membership of cited reference IDs. These checks do not verify whether a legal interpretation, reference application, or rewrite is correct.

Generation reserves an atomic Postgres budget before calling the provider: 50 attempts globally per UTC day by default, 10 per workspace. Failed attempts count. Cached reads do not. In-process duplicates coalesce; two instances can both generate, but both consume budget and return the single persisted winner. A revision change during generation produces 409 under the same case lock used by edits. Queue queries and normal case-detail responses do not join AI data or call the model.

## Review and refinements

GPT workers implemented API/storage and UI against shared contracts; root implemented the provider, integrated, evaluated, and deployed. Claude Sonnet 5.5 independently reviewed the implementation. Its three code findings were fixed: trim promoted concern fields for duplicate recognition, test the actual refusal response branch, and deduplicate validated reference IDs. GPT checked the fixes and subsequently clarified unknown-status wording and evaluation model overrides.

Live output inspection mattered beyond those code checks:

- An early marketing rationale asserted typical performance without evidence. The prompt now frames possible benefits as hypotheses.
- Browser testing of v2 falsely treated an APR range as a repayment-disclosure trigger. The [CFPB's §1026.24(d)(1) commentary](https://www.consumerfinance.gov/rules-policy/regulations/1026/24/) explicitly excludes an APR statement from those triggering terms. Bounded guidance now distinguishes APR-only text from an actual payment/repayment trigger.
- Claude's review of v4 outputs found qualifier scope changes, invented rate-check/speed claims, missing-context questions presented as concerns, and a marketing suggestion to drop a repayment term. V5 explicitly preserves qualification sentences, requires support for process/CTA claims, puts missing-context requests in questions, and avoids treating removal of a disclosure trigger as a marketing improvement.
- Medium reasoning and the more explicit constraints improved these observed outputs. Prompt tuning and a small evaluation do not establish reliable legal accuracy or resistance to all malicious instructions.

Previously saved test opinions retain their original prompt version and content. Deployment does not silently rewrite the historical record. A new revision gets a new opinion.

## Remaining limits

The model can still invent, omit, overstate, or misapply facts and requirements. Reference membership is not entailment; suggested language is not automatically fact-checked against the rule engine. Human review remains required, and opinions never clear blockers. A long response may hit the token/time limit and return an error while the ordinary workflow stays usable.

Anonymous demo workspaces are not authentication. A visitor can create more workspaces and exhaust the global daily allowance; the shared cap bounds generation attempts but does not guarantee availability. Browser cancellation does not necessarily stop a server-side paid call, which may finish and save. Usage counters currently have no retention cleanup. The deployed system is appropriate for this fictional public demo, not confidential customer submissions or production access control.
