# Next.js interface implementation handoff

Read docs/build-spec.md and packages/contracts/mod.ts. Own ONLY `apps/web/src/` and `apps/web/next-env.d.ts`. Root handles package/tsconfig/next.config installation and contracts. API and check-engine agents run in parallel. Do not change their files, install packages, commit, or delegate.

Implement the full useful interface in Next App Router with React, TypeScript and plain CSS. Installed dependencies: lucide-react and @fontsource/manrope. Import shared types/labels from @clearpath/contracts. No frontend imports of backend/check implementation. Fetch /api endpoints from build-spec; success is raw JSON. API results authoritative. Use x-demo-role header for actions; persist only role preference locally, never product records. API ready may lag; do not substitute fake successful responses or hardcoded findings.

Design: slate/navy sidebar with ClearPath logomark, review queue/submissions, offer library, restrained demo-workspace label. White/light cool workspace, teal primary actions, amber findings, Manrope typography. Crisp deliberate table with campaign title/publisher, product, format, findings, target date, status. Status tabs counts driven by returned cases. Useful toolbar and New submission button. Numbers represent workload, not claimed performance improvements. No generic dashboard charts.

Routes: / queue; /cases/[id] detail; /new submission; /catalog reference viewer. If easier, root page uses a client app with Next routing. Need meaningful loading/error/empty states, accessible controls and labels, keyboard focus, mobile stacking. Role switch Reviewer/Submitter prominent but quiet; same workspace accessible under both roles.

Detail: metadata header + exact revision; content pane left with safe escaped excerpt highlighting, checks pane right with status/source/why/suggestion, explicit text-only scope. Each finding/unknown supports confirm or dismiss (reason required for dismissal); reviewer can add manual concern and resolve with rationale. Header/footer allow copy approval or request changes via actual API; show server errors. Submitter sees requested feedback and can edit/resubmit; editing approved copy creates a new revision. Support side-by-side previous/current content, revision picker, and activity timeline. No auto-carrying dispositions. Current revision is detail.revisions.at(-1); old revisions read-only. Require expectedRevision for all mutations. Both buttons show pending disabled state.

Form fields match SubmissionInput: title/product/offer/publisher/format/launchDate/content/completeAsset/link-to-application/optional substantiation. Product chooses matching catalog offer, unknown option null. Allow self-check before submitting, render Analysis plainly. For edit, submit revision endpoint. New submission goes to returned detail. Clean approval one action once applicable concerns resolved; no universal rationale requirement for clean copy. Manual finding body {expectedRevision,title,quote,reason}, resolver {expectedRevision,resolution}.

Catalog viewer: show fictional terms and approved copy, version and notes. Allow copy example into new form if practical; don't add admin CRUD. Every visible action must work. Use local font imports, avoid runtime external images/fonts.

Verification: npm run typecheck --workspace @clearpath/web, npm run build --workspace @clearpath/web (root may run build). Backend may be pending; list integration uncertainty honestly. Do not add snapshot/UI text tests just to satisfy process; root does browser E2E. Write docs/handoffs/frontend-report.md with files, test results, any contract questions. Keep components reasonably split; prioritize functional working loop plus polished usability.
