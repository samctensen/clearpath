Use Deno/Fastify matching Atlas's patterns: createApiServer(dependencies) separated from listening startup; validated requests; service functions own workflow; SQL contained in model operation layer; explicit Result values for anticipated failures. Build independently testable DB/store and service. You may read Atlas architecture notes in project docs but no need to explore Atlas.

Use root deno.json import aliases. Shared contract types must match exactly. `analyze` arrives from @clearpath/checks; it may not exist yet. If you need to test while it is absent, message root; do not create a fake production analyzer. Model tests can proceed independently.

Storage: postgres.js for DATABASE_URL; local PGlite on .data/clearpath with same SQL and migrations. PGlite supports Deno. Production requires DATABASE_URL and COOKIE_SECRET (>=32 chars) and refuses fallback. Use transactions for revision+case update+audit and decisions; lock the case row, compare expectedRevision. Distinct relational tables for workspaces, cases, revisions, dispositions/manual findings, decisions/events. JSONB appropriate for immutable input+analysis snapshot, not one undifferentiated application blob. Model operations encapsulate SQL. Expose a factory allowing isolated in-memory PGlite tests. Numbered SQL migration + migration task. Startup may auto-migrate local only, production explicit migration command.

API endpoint schemas and state rules are all in build-spec. Fastify inject tests can test real routes without opening a port. Signed httpOnly workspace cookie; random per-visitor workspace, initialized with realistic fictional submissions (call engine to generate findings), existing cookie should not reseed. Do not create a public destructive reset endpoint. API should work at 127.0.0.1:8000, with cookie Secure only in production and SameSite=Lax. Body cap ~64KB. Mutations require application/json; reject disallowed Origin when present; Next proxy same-origin UI. Role header is explicit demo simulation. No secret headers, content, or DB URLs in logs/errors. Header choice doesn't establish real authorization, label this clearly in README API notes.

Seed ~6 cases from catalog, with mostly ready_for_review, one needs_information, one changes_requested, one approved. All through real service transitions where possible; timestamps can represent sample history but labels must stay demo. Include product+publisher variation.
